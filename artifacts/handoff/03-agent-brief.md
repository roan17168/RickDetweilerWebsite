# 03 — Technical brief for the coding agent

You are adding missing Revision 6 content to a static, dependency-free site. This document is the
contract: follow the patterns already in the repository instead of introducing new ones.

## 1. Rules that override convenience

1. **Revision 6 is the source.** Every sentence, label, question and result must trace to it or to
   an attachment the owner supplies. Never invent a statistic, quotation, citation, question,
   answer option, page name or PDF.
2. **Do not touch the legacy root pages** (`/index.html`, `/about.html`, `/choosing-a-college.html`
   and the rest at the repository root). They are the old live site. Work only in `src/`,
   `build.js`, `artifacts/` and the Markdown docs.
3. **Never hand-edit the repository root.** It is generated by `node build.js` and is disposable.
4. **No dependencies, frameworks, CDNs or third-party requests.** Vanilla HTML, CSS and JS only.
   Fonts are self-hosted.
5. **No commit, push, deploy or publish** unless the owner explicitly asks.
6. **Do not weaken an audit to make it pass.** When content legitimately changes, change the
   expectation with a comment explaining why (see `feature-audit.js`, “Closing block removed”).
7. If an attachment is missing a piece you need (a result's copy, a PDF, a field), stop and ask.
   Partial delivery with a written gap is acceptable; invention is not.

## 3. Build pipeline

`node build.js` reads `src/pages/<body>`, wraps it in the shell (head, header, footer, notes panel,
scripts), renders `{{TOKENS}}`, writes `<file>`, then writes `styles.css`, per-quiz data
globals, copies `src/scripts` and `src/assets`, and (with `SITE_URL`) writes `sitemap.xml` and
`robots.txt`.

A page is registered in the `pages` array in `build.js`:

```js
{
  file: 'tools/example.html',        // output path; 'tools/' triggers ../ path rewriting
  page: 'choosing',                  // body[data-page] used by ui.js
  title: '… | What College Is Really For',
  description: '…',                  // used for meta description, OG and JSON-LD
  socialDescription: '…',            // optional shorter social text
  body: 'tools/example.html',        // file under src/pages/
  scripts: ['example-data.js', 'example.js'], // emitted as scripts/…, then ../-rewritten
  notes: siteNotes.example,          // omit or [] for no notes panel
  robots: 'noindex,follow'           // optional; omission = indexable
}
```

For nested pages, `qualifyNested()` prefixes relative `href`/`src` values with `../`, except ones
already starting with `../`. Write links to root pages explicitly as `../choosing-a-college.html`
(see the scorecard).

`siteNotes` in `build.js` holds per-page notes arrays (`{ n: 1, text: '…' }`); the shell renders
them and the dialog. Data files are written as `window.WCIRF_<NAME> = <json>`; the page script
reads that global.

SEO is automatic: give each new page a unique title and description, add it to `pages`, and it
appears in the sitemap and JSON-LD when `SITE_URL` is set. With no origin, absolute tags are
skipped and `seo-audit` reports notes, not failures.

## 4. Tool-page pattern

Use `src/pages/tools/college-scorecard.html` as the template. Required structure:

1. `<section class="choosing-section choosing-scorecard-section" aria-labelledby="…">` wrapper.
2. One `<h1>` (the page title), then the tool's “What it's for” and “When to use it” paragraphs.
3. “How to use it” ordered list, then any rating/legend table with a `<caption>`.
4. The app mount: `<div data-<tool>-app>` plus `<noscript>` telling the reader the page still
   works in print.
5. A save note: state that it is saved on the device, and that Copy/Email/Print are available.
   Never say “Download as PDF” unless a real PDF is linked.
6. Print control: button adds `printing-<slug>` to `<body>`, calls `window.print()`, removes the
   class on `afterprint`; add `@media print` rules in the tool's stylesheet so a plain browser
   print also works.

State rules:

- localStorage key `wcirf_<tool>_v1`; store a versioned object, never free text with personal data.
- Restore on load; provide a clear/reset action with an `aria-live` status message.
- Every field labelled (`<label for>` or `aria-label`); fields grouped in `<fieldset>` with
  `<legend>`; `inputmode`/`autocomplete` where sensible; no placeholder-only labels.
- Keyboard: all actions reachable, focus moved to the result heading (`tabindex="-1"`), visible
  focus styles inherited from the design system.
- Copy uses `navigator.clipboard` with a textarea fallback; Email builds a `mailto:` body; never
  send anything to a server.

Where the tool replaces a page-level print card, update the owning audience page's card to link
the tool page and keep exactly one primary action.

## 5. Quiz pattern (Counselors)

Model the implementation on `src/scripts/faculty.js` + `src/data/faculty.json`, and take sharing
and persistence from `src/scripts/choosing.js`.

Data shape (`src/data/counselors.json`):

```json
{
  "quiz": {
    "id": "counselors",
    "intro": "…",
    "honesty": "Pick the answer that is true for you…",
    "skip": "Skip the quiz and go to the recommendations",
    "questions": [
      { "id": "cq1", "text": "…", "options": [{ "text": "…", "outcome": "Matchmaker" }] }
    ],
    "results": [
      { "id": "matchmaker", "heading": "…", "lead": "…", "questions": ["…"], "try": "…", "research": "…" }
    ]
  }
}
```

Follow the scoring model the attachment specifies. If it is a sum-of-points model, copy the
`scoreQuiz` shape from `faculty.js`; if it is outcome-based, copy `choosing.js`. Do not invent a
scoring scheme; if the attachment omits it, ask.

Result card must include: result title and lead, the finding, questions to ask, a way to check
without asking, “Try this one thing”, the collapsed research line, and Copy / Email / Share /
Retake. Persist the result under `wcirf_counselors_result_v1`. Share link format:
`#result=<slug>` (Choosing's format), reopened on load. Include the honesty line and a link to
The Research page. Any study named in the quiz gets a numbered note in `siteNotes.counselors`,
starting at 1, and the panel handles the rest.

Placement in `src/pages/counselors.html`: quiz block first in the hero, first question rendered
immediately, “Skip the quiz and go to the recommendations” directly under it, result card below
the hero and above the kit contents. The kit's eight sections and the print button stay.

Accessibility: `<fieldset>` per question with `<legend>`; radio inputs; `aria-live` status for
step changes; focus the new question heading; the result heading receives focus; support
`prefers-reduced-motion` through the existing `motionBehavior()` helper.

## 6. Downloads pattern

- Source files: `src/downloads/<name>.pdf`.
- Build: `fs.cpSync(path.join(SRC,'downloads'), path.join(OUT,'downloads'), {recursive:true})`,
  guarded by existence, with a log line.
- Link markup: `<a class="btn btn-outline" href="downloads/parent-checklist.pdf" download>Download the parent checklist (PDF)</a>`
  (on a root page; add `../` on tool pages).
- Keep the existing print control on the same page. Label print actions **Print**.
- PDFs must not enter `sitemap.xml`, must not be indexed as pages, and must not be tracked.
- If a PDF is generated from HTML, generate it as a committed build artifact outside the repository root
  and keep the source in `src/downloads/src/`; do not add a runtime dependency.

## 7. Notes and citations

```html
<sup><a class="source-note" href="#note-1" data-note="note-1" title="See source">1</a></sup>
```

Add the matching `{ n: 1, text: '…' }` to the page's `siteNotes` entry in `build.js`. Numbers run
from 1 in document order with no gaps (`rev6-audit` checks this). Every page that has citations
shows “Sources for this page” at the end (the shell does this); pages with no citations get no
panel.

## 8. Audits to add or update

- `rev6-audit.js`: remove the `counselors.html` exemptions from the quiz-mount and skip-link
  checks once the quiz exists; the BLOCKED lines for tool pages/downloads should be deleted only
  when the real pages and files exist.
- `counselors-audit.js`: add quiz assertions (question count, result count, skip link, result
  controls, notes) or add a dedicated `counselors-quiz-audit.js`.
- `feature-audit.js`: add expected counts for each new tool page and each download link.
- `qa-audit.js`: nothing special; it will check new internal links and fragments automatically.
- `seo-audit.js`: nothing to change; it walks every built HTML page, so missing titles or
  descriptions fail automatically.
- New `downloads-audit.js`: six files, `%PDF-` header, linked at least once, no 404.
- `browser-audit.mjs`: optional additions — one per new page for structure and console errors.

## 9. Accessibility and SEO checklist for every new page

- One `h1`; headings in order; no skipped levels.
- Descriptive title (≤ 65 characters) and description (70–165 characters), unique.
- Fields labelled; errors described in text, not colour alone.
- 44×44 px minimum targets; visible focus; no hover-only information.
- Images: meaningful `alt`, or `alt=""` when decorative; explicit dimensions.
- Print: header/footer/nav hidden, content visible, no clipped table columns.
- No third-party requests, no cookies, no analytics.

## 10. Report back

Give the owner: files added/changed, commands run with exit codes, audit before/after numbers,
any content you had to leave out and why, and a short list of what a human must still check
(screen reader, real PDFs, the domain). Do not claim testing you did not run.
